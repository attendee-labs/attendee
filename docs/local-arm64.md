# Experimental local ARM64 and FakeCloud development

These opt-in overrides add a native ARM64 web-adapter image and local S3-compatible storage. The default Dockerfile and development Compose remain unchanged. This is a contributed experimental setup, not a production deployment or a claim of full platform support.

## Scope and safety

- Debian Bookworm, system Python 3.11 and distro-provided ARM tini; not an exact Ubuntu/Python replica of upstream.
- Chromium and ChromeDriver **134.0.6998.88**, matching the version pinned by upstream, from Debian's official archive with SHA-256 verification. These old binaries have known security risks: use only for isolated compatibility testing with trusted meetings, never general browsing or sensitive logged-in accounts. A secure modern-browser migration is separate work.
- Python application requirements remain pinned as upstream, except the native Zoom SDK is excluded. Native Zoom is unavailable in this image; Teams and the optional webpage-streamer profile have not been validated.
- Allocate sufficient Docker VM memory. One test machine had only 963 MiB initially and experienced severe timeouts. Testing continued with 5 GB. This is an observed configuration, not a measured minimum.
- FakeCloud uses dummy credentials and is published only on host loopback. No Docker socket, cloud credentials or privileged capabilities are granted to it. Its volume can contain recordings/screenshots; treat it as sensitive local data.
- Obtain participants' permission and comply with meeting/organization recording rules.

## Start on Apple Silicon

Run from the repository root. The shell function below is for bash/zsh:

```bash
function dc() {
  docker compose -f dev.docker-compose.yaml -f compose.arm64.yaml -f compose.fakecloud.yaml "$@"
}
dc config --quiet
dc build attendee-app-local
```

Generate the environment only on a fresh setup; do not overwrite an existing file. AWS fields generated by init_env.py may remain empty when the FakeCloud override is used. The override sets dummy credentials explicitly.

```bash
if [ ! -e .env ]; then
  (umask 077; set -C; dc run --rm --no-deps attendee-app-local python init_env.py > .env)
fi
dc up -d postgres redis fakecloud
dc run --rm --no-deps attendee-app-local python scripts/init_local_s3.py
dc run --rm --no-deps attendee-app-local python manage.py migrate
dc up -d --no-build
dc logs attendee-app-local
```

Open http://localhost:8000, register a local account, confirm using the link printed in application logs, and generate a local API key. This is not a hosted Attendee account or Google API key.

For ARM with real S3, omit compose.fakecloud.yaml and configure your own storage in .env. For FakeCloud on the default Intel image, omit compose.arm64.yaml and use the normal image build. FakeCloud alone does not make the default image ARM-native.

Use the same Compose file combination for subsequent commands. To rebuild without interrupting an active meeting, build first, then recreate services only after the bot has left. Recreating the worker terminates bots running inside it.

## Local S3 details

FakeCloud 0.50.0 persists state in a named volume. The endpoint is http://localhost.localstack.cloud:4566: Docker DNS resolves this alias to the emulator internally; public DNS normally resolves it to loopback in the host browser. This is a hostname convention, **not a LocalStack dependency**. If local DNS/rebinding protection blocks the hostname, configure a local host/DNS mapping and preserve the same hostname for signed URLs.

Run python scripts/init_local_s3.py inside the app container to create the bucket and test PUT, GET and a presigned GET. It refuses non-local endpoints and removes its own test object. For persistence testing, put a temporary test object, restart only fakecloud, GET the object, then delete that temporary key. Do not delete the volume unless you intend to lose its contents.

**Known limitation:** with FakeCloud 0.50.0 and the current SDK/storage combination, HEAD/exists can return 404 for an object that LIST and GET can read. Uploads and presigned GETs passed; this does not establish complete S3 compatibility. The smoke script reports this condition as a warning. Earlier failed debug screenshots are not reconstructed by configuring storage afterward.

## Real meeting test and integration boundary

On an Apple M3 Max MacBook Pro (14 CPU cores, 36 GB RAM), macOS 27.2, Docker 29.8.2, Compose 5.6.0, linux/aarch64 daemon with 5 GB VM RAM:

- Native image built; app, scheduler, worker, Postgres and Redis started; migrations and HTTP login page passed.
- An initial ARM image using Chromium/driver 155.0.8059.79 left the automated browser on data:, and timed out at name_input. An isolated browser could load Meet. More RAM alone did not resolve that automation failure.
- Pinning Chromium/driver 134.0.6998.88 allowed the bot to fill its name, mute microphone/camera, request admission, and join a real Google Meet after host admission. Logs reported Successfully joined meeting; the host confirmed the bot was visible.
- Participant names and distinct platform UUIDs were populated, including two connections sharing one display name.
- The meeting test used recording_settings.format = none and platform captions, without paid transcription credentials. The internal joined_recording state is not evidence that an audio/video file was saved.
- Local S3 PUT/GET, Django upload/presigned download and object survival after a FakeCloud restart were observed. HEAD/exists remains a known discrepancy.
- Per-participant PCM streaming, overlapping-speaker isolation, DSH integration, Teams, Zoom, long recordings and production isolation were **not validated**.

## Getting audio rather than just joining

FakeCloud stores files; it is not a live audio receiver. Create a bot with websocket_settings.per_participant_audio pointing to your own **wss://** receiver. The current API rejects ws://. The receiver certificate must be trusted by the bot container; a self-signed certificate is not sufficient without a configured trust chain. No TLS verification bypass is included here.

Audio messages contain bot_id and data.participant_uuid, data.chunk (base64 mono 16-bit PCM), data.sample_rate and data.timestamp_ms. Resolve names through GET /api/v1/bots/{id}/participants: match data.participant_uuid to the returned uuid, not id or display name. Keep separate buffers per bot and participant. Duplicate names are possible; IDs identify platform connections, not guaranteed distinct physical people.

This contribution does not add a receiver or speech-recognition pipeline. The tested bot had no streaming destination; joining alone does not deliver audio to a consumer. The current PATCH schema does not expose websocket_settings, so configure it when creating the bot.
